# Nimbus VS Code Extension — Claude Code Context

## What this is

`nimbus-vscode` is the VS Code / Open VSX extension for [Nimbus](https://github.com/nimbus-agent/Nimbus), a local-first AI agent framework. It is a **thin client**: it talks to a locally-running Nimbus Gateway over JSON-RPC IPC via the published `@nimbus-dev/client` package and never calls cloud APIs itself.

Extracted from the Nimbus monorepo (`packages/vscode-extension`) on 2026-06-22 so it can release independently of the Gateway.

## Architecture (load-bearing)

- **IPC-only.** All Gateway interaction goes through `@nimbus-dev/client` (published to npm). There are no direct cloud/network calls and **no imports from the Nimbus gateway source** — the only Nimbus dependency is `@nimbus-dev/client`.
- **Bundled.** `esbuild.mjs` bundles `src/extension.ts` (node CJS) and the webview entry `src/chat/webview/main.ts` (browser IIFE) into `dist/` + `media/`, with only `vscode` external. The published `.vsix` therefore has **no runtime npm dependency** on `@nimbus-dev/client` — it's inlined at build time; the dep is build/typecheck-time only.
- **Surface today:** Ask (streaming chat panel, with a **Stop** button that cancels an in-flight generation via `cancelStream`), Search (Quick Pick over the local index), Ask/Search Selection, **Find related** (pivot from a selection or Index item to ranked neighbors via `searchRanked`), **Quick Ask** (one-shot editor quick-ask over `agentInvoke` — reply in a read-only tab, no chat panel), **diagnostic actions** (up to three Nimbus entries on the lightbulb of an error or warning diagnostic — `Explain this problem` and `Suggest a fix` (the reply, asked for as **whole lines**, spliced into a diff against the real file, never an applied edit) via `agentInvoke`, gated, plus `Find prior occurrences` via `searchRanked`, which reaches no model and so is ungated, though it still needs the Gateway socket, is only as good as what is indexed, and is withheld when the normalized query is too short to be worth searching — which is when the lightbulb shows two rather than three; `Information`/`Hint` diagnostics are never offered, and where a line carries several diagnostics exactly one is chosen so the lightbulb never grows past three entries; command-only actions carrying no `edit`, so selecting one never applies a change and never routes around the gate's cancel path, and none sets `isPreferred`, so Auto Fix cannot fire a gated model call; toggle `nimbus.diagnostics.showCodeActions`, `src/diagnostics/` — verified in a real editor 2026-08-13 against Gateway 2.2.0 (three entries on an error, none per diagnostic, none from Auto Fix, none on a Hint; the two-diagnostics-on-one-line labelling case still unchecked)), the **built-in briefs** (`Why is this here?`, `Who knew this code?`, `Who else is touching this?` from the editor context menu, plus `Team huddle`, `Is this idle?` and `Safe to deploy?` from the palette and the Agents sidebar view — the latter two prompt for their input (a resource ref, or a ref plus namespace) since a palette or sidebar entry carries no editor context — `agentsWhy` / `agentsGhost` / `agentsConflicts` / `agentsHuddle` / `agentsJanitor` / `agentsPreflight`, each behind the pre-flight gate under the `"brief"` kind) plus **blame on hover** (`agentsWhyPeek` — author, commit subject, PR and ticket for the line under the cursor, with a `Why? →` link into the full brief for that same line; ungated because it reaches no model, and a test asserts it is the only exemption; toggle `nimbus.briefs.showHoverBlame`, needs `nimbus init` to have indexed the repo root), the **`@nimbus` Chat participant** (native participant in VS Code's built-in Chat view — the ops slash commands `/incident`, `/deploys`, `/owns`, `/blast`, `#file`/selection context, streaming answers via `askStream`, local-index citations via `searchRanked`; the Copilot three — explain/fix/test — were retired to Quick Ask presets in PR #49); the **Language Model tools** `nimbus_search` + `nimbus_ask` (`contributes.languageModelTools`, so other chat extensions and agents can call Nimbus as a tool — `src/lm-tools/`); a **dev-workflow trio** over the built-in git extension — `Generate Commit Message` (staged diff → SCM input box, matching the repo's own commit style), `Review Changes` (staged + unstaged local changes → a findings tab naming what wasn't reviewed), and `Generate Tests` / `Generate Docstrings` (editor selection → untitled test buffer / docstring diff) — all via `agentInvoke`, output always a suggestion, never an applied edit; a Nimbus activity-bar sidebar with **Audit**, **Sessions** (with chat resume), **Index**, **Agents** (two groups: the built-in briefs, and the chat scopes from the `nimbus.agents` setting — so the view is never empty on a fresh install), **Workflows** (one row per saved workflow from `workflowList`, its recent runs from `workflowListRuns` loaded **on expand** — the one view using `createDataView`'s optional `loadChildren`, since eager children would cost an RPC per workflow on every open), and **Connectors** (`nimbus.connectorsView`, the eighth container view, `src/connectors/` — one row per connector from `connectorListStatus`, sorted unhealthy-first (`error` → `backoff` → `paused` → `syncing` → `ok`, ties on `serviceId`); `enabled: false` overrides the icon and the row reads *disabled* regardless of status; description is sync telemetry (`1,204 items · synced 3m ago`, or `never synced`), tooltip carries depth/interval/next-sync/failure-count and the connector's `lastError` **verbatim** — never logged, since it is the user's own information about their own connector and nothing here leaves the machine. Recent syncs (`connectorStatus`) and health-state history (`connectorHealthHistory`) load **on expand**, the same `loadChildren` pattern as Workflows; an `mcp_*` id skips the history call rather than surfacing its rejection, since that RPC accepts built-in ids only. Nine commands — sync, full re-sync, pause, resume, configure, re-index, authenticate, add MCP connector, remove, plus a separate `nimbus.refreshConnectors` — all palette-visible, prompting with a `QuickPick` when invoked without a row; every mutation is normalised by one adapter (`src/connectors/connector-client.ts`) into `applied` / `denied` / `failed` across the suite's four different failure shapes, so a consent denial (`connectorAddMcp`, `connectorRemove`, and a full-depth `connectorReindex`) is never reported as a failure, and its `reason` is shown verbatim rather than asserting a person declined, since an expired-unanswered consent request arrives as the identical shape. The two HITL-gated calls get a non-cancellable "waiting for your consent…" progress notification and no extension-side timeout — none of the connector methods takes a `timeoutMs`, so the wait is bounded by the Gateway alone. Credentials are collected via masked `showInputBox` prompts from `AUTH_CATALOG` (field names sourced only from the pinned client's JSDoc for `ConnectorAuthParams`, since the Gateway's own handler may not be read — AWS is deliberately absent because the JSDoc names `awsAccessKeyId` but not its secret counterpart) and passed straight to `connectorAuth`; an unrecognised `serviceId` falls back to a generic one-field-plus-add-another flow. The extension never stores, caches or logs a credential value — a test asserts a sentinel value reaches neither the logger, a dialog, nor a progress title. No new outbound path: none of the twelve `connector*` RPCs takes a prompt or returns a completion, so this surface, like *Find related*, sits outside the pre-flight gate) views, plus the **ambient context panel** (`nimbus.contextView` — the one `WebviewView` in that container and the view it opens on, `src/context/`: a pure core plus `real-context-view.ts`, the only file there touching `vscode`. It follows the active editor debounced (selection 300 ms / editor 150 ms / diagnostics 500 ms), collects nothing while hidden, and shows five signals: the file's errors and warnings, the branch of the repository *containing that file* (chosen by longest root prefix via `repoContaining`, not the git extension's first repo) with a count of files not yet committed (the union of `changedPathsNow`, unstaged, and `stagedPathsNow`, index vs `HEAD` — counting either group alone, as it did before, made the count fall the moment a file was staged — both read off the git extension's already-materialised state, never a `git diff` subprocess, since this runs on every tick; the row is omitted on a clean tree rather than shown as zero), who last touched the line under the cursor (`agentsWhyPeek`, through `whyParams` — that parameter is one-based and the snapshot's line is not), and the local index's nearest neighbours of the file or selection (`searchRanked`); and **Sources** — a fifth signal, shown only when at least one connector is `error` or `backoff` (a paused or disabled connector is a state the user chose, and raises no row here), reading the `ConnectorHealthSummary` the status-bar poll already computed rather than making a Gateway call of its own, and rendering nothing at all on a healthy setup (`SignalSection.suppressWhenEmpty`) rather than an always-present "all fine" line; plus the briefs whose required context is satisfiable right now — derived from `BRIEF_CATALOG` so a new brief is offered for free, pre-filled with an `EditorTarget`. **It talks to the Gateway on its own, with no user action:** on each debounce tick it sends the repo-relative path, the cursor line, and — when there is one — the selected text (clamped to 300 chars) to the *local* Gateway. Both calls **reach no model**, exactly as the hover blame and *Find related* do, so both stay outside the pre-flight gate; `src/context/` reaches neither `agentInvoke` nor `askStream`, and `test/unit/egress-choke-point.test.ts` fails if it ever does. Collapsing the view stops collection entirely; a `nimbus.context.enabled` toggle (default `true`) switches it off while it stays open, leaving the view visible and saying so rather than going blank. Every offer routes to an existing gated command, and the two trust boundaries are explicit — webview→host validates a catalog-derived command allowlist *and* per-command arguments before any `executeCommand`, host→webview checks a `vscode-webview://` origin and the payload shape. Ships a second webview bundle, `media/context.js` + `media/context.css`, copied not bundled for the CSS. Collections are cached, coalesced and fenced by a pure `controller.ts` (an LRU per signal, keyed on what that signal actually depends on, with a per-signal invalidation epoch); each Gateway-backed section is posted as it resolves, while the local ones ride the first render. A real-editor pass on 2026-08-17 against a live Gateway (`docs/superpowers/plans/2026-08-17-context-panel-f5-findings.md`) drove the offers, the gate, blame accuracy, connect/disconnect and the git watcher, and found four suspected defects real and fixed — Related repeating the open file's own symbols (now excluded by an exact `rawMeta.file`-to-`repoPath` match plus a dedupe, not the old exact name-equality check (`i.name !== snapshot.path`), which never matched), the changed-file count falling when a file was staged (see above), the redaction note's false claim over a repo-relative path (now three-state — bare, relative, or absolute — and conditional on what the payload actually contains), and the panel logging nothing (now one debug line per collection, naming each signal cached/local/fetch/skipped). The fifth, the panel's rendered height, turned out not to be a manifest question: a follow-up isolation pass showed the `initialSize`/`visibility` hints inert, since a fresh profile already opens the Context view full-height — VS Code's own default for a webview view placed first in a container — with or without them; the manifest reverts to what it was before this branch. The ~140px case from the original pass was a profile carrying a layout stored from an earlier version, which no manifest default can rewrite — there the fix is the user's, collapsing the other views or dragging the sash. Multi-root windows, focus survival, and the typing-storm cadence were not run — see the findings doc for the full list); the **workflow run surface** (`Run Workflow` / `Dry-Run Workflow` from the palette or a Workflows row's context menu — `src/workflows/`, streaming per-step output into a `Nimbus Workflow Runs` output channel under a cancellable progress notification, then a read-only run report; cancel goes through `workflowCancel` and lands **at the next step boundary**, so the in-flight step always finishes — every string the surface shows says so rather than implying an instant stop); the **"Preview what leaves" pre-flight gate** (every agent-bound call routes through `src/egress/gated-client.ts`: the five `agentInvoke`/`askStream` paths, the six prompting brief calls, the **diagnostic actions** (kind `"diagnostic"`, one skip key covering both `Explain this problem` and `Suggest a fix`), the **workflow run** (kind `"workflow"` — the one surface whose preview is a *manifest* rather than the literal bytes, since the extension sends only a workflow name and the Gateway expands the saved steps; `buildRunManifest` states that in its omissions instead of implying byte-exactness, and the gate is awaited *before* the stream starts), and the participant's three ops briefs (`agentsCatchup` / `agentsExpert` / `agentsImpact`), which record rather than prompt — a modal must not interrupt a chat turn, and a slash-command argument is text the user just typed — with `agentsWhyPeek` the sole exemption; the surfaces where the extension chooses the content — Quick Ask, the SCM trio, the diagnostic actions, and the briefs — show a modal manifest of exactly what would be sent, with a *Show full text* escape hatch and a per-surface, per-workspace *Always send here*; `nimbus_ask` confirms inline via `prepareInvocation`; Ask panel and participant route and record without prompting; commands `Show Last Outbound Payload` / `Reset Egress Preview Prompts`; **no RPCs**, works while disconnected); an **Egress** ledger viewer (with Verify-ledger and Prove-window commands, the after-the-fact counterpart to the gate) plus an **egress status-bar badge** (row count + ledger-live ✓ via `egressHead`; shown while connected, on by default, toggle `nimbus.egress.showStatusBarBadge`); a **connection troubleshooter** (state-aware modal, no RPC); a **Get Started walkthrough** (first-run onboarding via `Nimbus: Open Walkthrough` / the Welcome page, no RPC); a status-bar quick menu and connection + HITL plumbing; plus **Restricted Mode** support (`capabilities.untrustedWorkspaces` = `limited`, `extensionKind: ["ui"]` — in an untrusted workspace the workspace-level `nimbus.socketPath` and `nimbus.autoStartGateway` settings are ignored). For where this is going, see [docs/ROADMAP.md](docs/ROADMAP.md) (phased by SDK-readiness). The **share** surface is **not implemented yet** — it is blocked upstream, not deferred by choice: no published `@nimbus-dev/client` exposes those RPCs (checked through the pinned client — see `package.json`), and the non-negotiable below forbids reaching past the typed client. Connector management has **shipped** — see **Connectors** above and `docs/connectors.md` — using the full `connector*` suite (incl. `connectorReindex`, `connectorAddMcp`) and `subscribeConnectorConfigChanged`. What it still cannot do: onboard a *built-in* connector, since no RPC registers one (`connectorAddMcp` only registers an MCP source, and `connectorListStatus` returns only already-registered connectors — standing one up stays a CLI job); and show a registered MCP connector's command line, since `commandLine` is an input to `connectorAddMcp` and appears in no result or status type the pinned client returns. The workflow family is now **monitor + run + cancel**; authoring (`workflowSave` / `workflowDelete`) is deferred on purpose — `steps_json` is opaque at save time, so a malformed DAG saves cleanly and fails only at run time.

## Layout

- `src/` — extension-host code (`extension.ts` entry); `src/workflows/` (the run surface — pure `run.ts` (manifest, outcome wording, run report) plus the `vscode`-shaped `commands.ts`); `src/egress/` (the **pre-flight gate** — `gated-client.ts` is the only file in `src/` allowed to touch `.agentInvoke` / `.askStream`, guarded by `test/unit/egress-choke-point.test.ts`; plus pure `leak-check.ts` / `preflight.ts`, the `gate.ts` decision table and `skip-store.ts`); `src/chat/` (chat controller/panel + `webview/` browser bundle); `src/sidebar/` (activity-bar tree views — audit, egress, sessions, index, agents, workflows — plus quick-actions, over a shared `tree-view.ts` seam); `src/scm/` (dev-workflow trio: pure diff/commit-message/review/generate modules plus `commands.ts`, behind a `GitApiLike` seam over VS Code's built-in git extension — `real-git.ts` is the only file that touches it, mirroring `src/chat-participant/real-participant.ts`); `src/lm-tools/` (the `nimbus_search` / `nimbus_ask` Language Model tools — pure handlers plus the `real-lm-tools.ts` vscode-glue adapter); `src/briefs/` (the built-in briefs — pure `catalog.ts` / `render.ts` / `params.ts` / `peek.ts` / `peek-hover.ts` / `namespace-store.ts`, plus the `vscode`-touching `commands.ts` and `real-hover.ts`; gated calls route through the egress gate under the `"brief"` kind, `agentsWhyPeek` is the one documented exemption); `src/diagnostics/` (the lightbulb actions — pure `normalize.ts` (diagnostic message → index query), `context.ts` (diagnostic + document → payload context, with splice offsets expanded to **whole lines** so they match what `prompts.ts` asks the model to replace), `prompts.ts` and `actions.ts` (which actions to offer, and the one diagnostic they are offered for), plus `commands.ts` over injected deps and `real-provider.ts`, the only file here touching `vscode`); `src/connectors/` (the Connectors view and its nine commands — pure `health.ts` (`summarizeConnectorHealth`, moved here from `src/status-bar/` once it gained a third consumer), `catalog.ts` (the credential-field catalog, sourced only from the pinned client's JSDoc and documented as apt to drift), `rows.ts`, `outcome.ts` (the `applied`/`denied`/`failed` adapter over four wire shapes), `interval.ts` (human interval strings ↔ ms), plus `connector-client.ts` (the `ConnectorClientLike` seam) and `connectors-view.ts` (`createDataView` with on-expand `loadChildren`, the Workflows pattern) — and `commands.ts`, the one file here holding injected `vscode`-shaped deps; reaches no model, so it sits outside the pre-flight gate; see `docs/connectors.md`); `src/connection/`, `src/hitl/`, `src/status-bar/`, `src/logging.ts`, `src/settings.ts`
- `src/vscode-shim.ts` — the seam over the `vscode` API (stubbed in tests via `test/unit/vscode-stub.ts`)
- `test/unit/` — Vitest unit tests; `vscode` is aliased to the stub in `vitest.config.ts`
- `esbuild.mjs` — build
- `scripts/` — Node ESM maintenance helpers: `clean.mjs`, `check-bundle.mjs` (guards the no-runtime-dep bundling invariant), `check-vsix-contents.mjs` (guards what the `.vsix` ships), `check-settings-docs.mjs` (guards settings-doc drift); plus `secret-health.ts`, the tested classifier behind `secret-health.yml` that keeps a rejected publish token apart from one merely approaching a known expiry. See `scripts/README.md`.
- `docs/` — contributor/maintainer reference: `architecture.md`, `connectors.md`, `development.md`, `settings.md`, `releasing.md`. See `docs/README.md`.
- `.github/workflows/ci.yml` — typecheck + lint + check-settings-docs + test + build + check-bundle + check-vsix-contents on PR/push (Ubuntu), plus a lean Windows job (typecheck + test + build + the two bundle guards). The ExTester/Selenium UI suite (`bun run test:ui`) is not part of CI — see `docs/development.md`'s UI tests section — because of an unfixed upstream headless-Linux limitation in ExTester's window-reuse handshake.
- `.github/workflows/publish.yml` — on a `v*` tag: Marketplace + Open VSX + GitHub Release
- `.github/workflows/dependabot-lockfile.yml` — one of the two `pull_request_target` workflows here (a write-capable token over a PR author's tree); the other is `.github/workflows/cla.yml`, which is likewise write-capable (`actions: write`, `pull-requests: write`, `statuses: write`). Its four defences — the `dependabot[bot]` actor gate, `bun install --ignore-scripts`, `persist-credentials: false`, and a `head.sha`-pinned checkout — are pinned by `test/unit/dependabot-lockfile-workflow.test.ts`; change one and that test tells you.

## Commands

```bash
bun install
bun run typecheck     # tsc --noEmit (strict)
bun run lint          # biome check . (whole repo)
bun run test          # vitest run
bun run test:ui       # ExTester/Selenium UI suite against a real VS Code (needs a desktop session, or xvfb-run on Linux)
bun run build         # esbuild bundles
bun run watch         # esbuild bundles, rebuild on save
bun run check-bundle  # assert vscode is the bundle's only external (run after build)
bun run check-vsix-contents  # assert the .vsix ships only allowlisted files (run after build)
bun run check-settings-docs  # assert every nimbus.* setting is documented
bun run package       # .vsix via vsce (--no-dependencies; esbuild already inlined deps)
```

## Conventions / non-negotiables

- TypeScript **strict**; **no `any`** (use `unknown` for external data). Biome enforces this (`noExplicitAny`, `noConsole` in `src/`, `noNonNullAssertion`, …) — see `biome.json`. Log via the output channel (`logging.ts`), never `console`.
- The committed `@nimbus-dev/client` dependency is always a **published** version (`^x.y.z`), never `workspace:*` (that only resolves inside the monorepo).
- Don't reach into the Nimbus gateway. New Gateway capability is surfaced by bumping `@nimbus-dev/client` and using its typed IPC client.
- Keep `src/` and `test/` self-contained; the `vscode` API is only touched through `vscode-shim.ts`.

## Releasing

1. Releases are automated with **Release Please**. Land PRs with Conventional-Commit titles (the repo squash-merges, so the PR title is the commit `release-please.yml` reads); it keeps a standing release PR that bumps `package.json` and writes `CHANGELOG.md`. Never hand-edit the CHANGELOG or tag by hand.
2. Merging that release PR creates the `vX.Y.Z` tag → `publish.yml` stamps the version **from the tag**, publishes to the VS Code Marketplace + Open VSX, and mirrors the `.vsix` on a GitHub Release. Pushing a tag by hand is the documented fallback only.
3. Requires repository secrets `VSCE_PAT` (Azure DevOps, "Marketplace (Manage)") and `OVSX_PAT` (Open VSX namespace `nimbus-agent`), plus the **organization**-level `RELEASE_BOT_CLIENT_ID` / `RELEASE_BOT_PRIVATE_KEY` App credentials that mint the release-please token (a tag pushed by `GITHUB_TOKEN` would not fire `publish.yml`). The `publish` job declares `environment: release`, which now restricts deploys to `main` + `v*` tags, but both publish secrets are still configured at the **repository** level — so every workflow on this repo can read them until they are re-added as environment secrets and the repo-scoped copies deleted. See [docs/releasing.md](docs/releasing.md).
